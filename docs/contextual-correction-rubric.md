## 实施隔离与接口

本文件含未见题目和独立答案标准，只供负责验证的 agent/审阅者使用。**不得把整份 Markdown、验收段、后续用户 turn、原24轮预期答案交给 host、extractor、selector 或 answer model。实现者在通用修复冻结前只接收覆盖/接口概览，不接收题目及具体期望事实。** 这次冻结后不按模型输出修改文本或期望；新增版本须另建文件并保留本版。

将下方唯一 `json` 代码块逐字提取到私有的新 scenario 文件时，可复用现有 runner 的 `--scenario` 接口；不修改原冻结 fixture。验收段始终分离存放。runner 仅逐轮给 `host.turn(text, turn_id, session_id, timestamp)`；host 不得读取场景元信息、全脚本或验收。使用实际 API 抽取→治理写入→受控读取→选择→回答，不能手工 seed 记忆或预填助手答案。

- `memory`：每轮真实抽取、v2 治理与 provider 回答；只用最近2组 user/assistant 历史和受控记忆。
- `recent_only`：相同模型、参数、用户 turn、模拟时刻与2组历史窗口；无记忆读写，不共享另一组助手回答。
- 两组各自跨 session 清空近期历史；每次运行 fresh user/DB，项目显式开启、global 不默认开启。双方都不持有对方答案或未来 turns。
- `timestamp = clock_origin + day_offset + hours_offset`，不要额外按轮数加分钟；所有状态比较使用模拟时刻，避免把过期当作纠错效果。
- runner 当前固定时钟起点与本脚本一致；若以后 runner 改时钟，须显式支持 `clock_origin` 或在运行前确认映射，不静默改测试语义。
- 每个 arm 的实际 request body、recent buffer、所有提案及拒绝理由、写入操作、完整 governed pool、选择ID、最终编译context与原始回复都保留。保存代码/source哈希、场景哈希、本验收哈希和对照参数。
- 原runner manifest中的 `rubric_sha256` 仍可能指仓库原评价标准，不能把它冒充本验收哈希；本计划哈希应单独记录在离线评审证据中，不能传给模型。
- 真实调用需由主线程按用户授权统一启动；本计划不发起调用，也不调整额度。完整16轮两组预计最多64次逻辑completion（记忆组抽取+选择+回答，对照组回答），空候选时可能更少，重试与实际收费另计。

## 独立验收（只给离线审阅者，不给模型或实现者）

### 证据分层与结果标签

每项分别记录：A 用户脚本所述要求；B 实际 model request / response；C governed store、candidate pool、selector 与最终 prompt；D 审阅判断。不能仅凭回答听起来合理判定记忆生效，也不能仅凭未形成画像就判定产品不具备该能力。使用 `PASS`、`FAIL`、`NOT_EXERCISED`、`INCONCLUSIVE`；缺失日志、画像未建立或基线无法区分时注明原因。任何一项不以模型自述“我已记住/更新”作为证据。

1. **临时短答不转为稳定偏好（H07→H08，H15→H16）**
   - H07 当前回答应满足一句短话；H15 应只交付一条六字文案，不加解释或询问。文案不预填；只检查含义与当前形式。
   - H07/H15 不得形成用于之后轮次的“默认简短/低细节”偏好或支持这类画像的持续证据；允许保留审计或当前请求记录，须区分记录与可用长期偏好。
   - H08 不重申长期学习偏好，也已切换会话。应先用可理解的小例子区分幂等/去重，再说明机制与关系，而不是沿用电梯里的短答约束。H16 应完整覆盖已知回顾与安排，不受 H15 单行文案限制。
   - 在 H07 前后与 H15 前后比较 preference/profile/evidence，检查后续 selection 和实际系统输入；不能用总字数作唯一质量指标。

2. **明确反证撤销旧沟通画像，保留未被否定的情境信息（H02/H03→H10→H13/H14）**
   - H02/H03 是不同真实 source turn，明确建立“无需缓冲、直接指出”的旧默认；检查其是否形成持久偏好和/或派生的高直接性画像。仅复制同一 source 不算独立支持。
   - H10 是对旧要求的明确替换，不是简单叠加一条“温和”提示。H13/H14 的最终 prompt 不应继续携带旧的“无需缓冲/硬直言”指令或同义相冲突策略；相关旧画像必须退休、替代或在读取时撤销，不能靠新回答偶然遵从新值掩盖旧画像仍在交付。
   - 新默认要求先简短承认合理处，再温和而明确地指出问题；不要求固定措辞、套话或一律夸奖。不得把“温和”误当“不指出问题”。
   - 旧高直接性画像若从未形成，本项画像撤销结论必须标 `NOT_EXERCISED`，同时另判显式偏好替换是否通过；不得把未触发等同通过。检查新旧 source attribution 与 final policy，不能要求某个内部 key 名称。

3. **工作评审与学习解释共存（H04/H05→H08/H09；H10→H13/H14）**
   - H08/H14 学习解释采用先例子、再原理的充分说明；不要为了工作评审短结论而省掉核心因果，也不要求无关长篇。
   - H09/H13 工作评审先给能否推进的判断，再抓一两处关键缺口；避免自动变成概念教学。H13 同时应用已纠正的温和默认，不复活旧硬直言。
   - H10 明确保留两个情境习惯；之后不能将二者合并为全局“总是简短”或“总是详细”，也不能把温和修正误作删除学习/评审偏好。
   - 审阅行为与保存/交付的适用范围。两种情境的答案长度差只是辅助证据，内容组织、问题覆盖与 scope 才是主要依据。

4. **忙碌状态被显式替换，不等 TTL 自然到期（H06→H11→H16）**
   - H06 为36小时短期状态，合法到期应从 H06 的模拟时刻推算；H11 发生在该窗口内，H16 仍在原窗口内。因此最终不再使用忙碌不能归因于过期。
   - H11 把当前可投入量明确改为每天一小时半。到 H16 应按此容量规划，不再按每天二十分钟缩减，也不因两条记录都存在而要求用户再次选一个。
   - 检查已存状态、冲突/替代关系、selector 与实际 prompt，旧记录可保留审计，但不能继续作为当前限制。不得将短期状态推断为人格或永久能力。

5. **跨会话旧项目决定与理由的实际召回（H01→H16）**
   - H16 应回顾双联纸质交接单；原因包括库房金属门关闭时信号不稳，以及值班员需要留一联。
   - 首版暂不做押金收款和自动逾期催还。可补充工具范围，但不要扩充未由用户决定的功能边界。
   - 以上答案依据必须能追溯 H01 经真实抽取/治理形成的记录，最终位于允许的候选与真实 answer request；不允许手工写入、读取原始全历史、把本验收文字塞进摘要、或事后修补答案。
   - H16 的近两轮窗口只有 H14/H15；H01 远离窗口且已跨两次 session。`recent_only` 应坦诚指出缺少旧决定，允许部分一般性建议，不能靠猜中片段计为成功回忆。
   - 同时检查无错误添加“扫码登记”、不存在的技术选型、已实施外部动作等。精确短语匹配只辅助核对，允许忠实同义表达。

6. **无需逐项确认且不会机械展示记忆（全程，重点 H10/H11/H13/H14）**
   - 普通清晰偏好和状态修正直接生效，不默认逐项询问“是否确认存储/是否确认画像/要不要记住”。不因模型推断就把每项转成待确认。
   - 允许对真正影响当前任务、脚本未给出的关键歧义作简短澄清，但须列明该歧义，不能笼统把所有追问判错。
   - 回答不反复用“我记得你”或标签证明记忆；H16 用户主动追问旧决定时可以说明来源。评价自然度需人工看完整回答，不靠禁词一票否决。

### 对照及归因矩阵

| 被测点 | 对照组能说明什么 | 不能据此夸大的结论 |
| --- | --- | --- |
| H08/H09 跨会话不同风格 | 对照无旧偏好；两组都能靠常识答好，必须结合 trace 才能判记忆适配 | 不把一次更长/更短回复当作整体自然理解收益 |
| H13/H14 跨会话新默认与双情境 | 两组都看不到 H10 原文，只有记忆组可有受控记录；检查旧策略是否撤销 | 未建立画像时不能宣称画像纠错已通过 |
| H16 项目理由/暂缓功能 | 对照窗口不含 H01，可明确区分真实召回与一般建议 | 不把猜中部分事实算有来源的记忆成功 |
| H16 当前容量 | H11 不在该 session 窗口，且原 busy TTL 尚未自然到期 | 不能只依据到期过滤而宣称显式状态替换有效 |

### 验收汇总规则

- 不用单一总分掩盖权限/来源/反证失败。分别报告临时约束隔离、旧画像撤销、情境共存、状态替换、项目召回、交互自然度六项及其证据链接。
- 最低通过门槛：两组16轮均执行完成；运行边界无答案/验收泄漏；H01关键事实与理由在 H16 有最终交付来源；H11容量替换有效；临时约束不变长期偏好；旧冲突策略不再进入后续 prompt；两个情境可共存；没有默认逐项确认。
- 对“画像撤销”还须旧画像确实成立且后续不复活，否则 `NOT_EXERCISED` 并提出下一次如何补测，不能临时改脚本或手工 seed 以让本次通过。
- 若原始答案不符合预期，保留失败。先定位抽取、治理、冲突/依赖、候选池、selector、编译还是生成阶段；之后修通用实现，用新 run 目录重跑完整固定脚本。阅读此验收后对失败做修复，结果即是同套回归，不再称首次未见验证。
- 本计划仅验证受控合成条件，不代表真实用户接受、长期稳定理解或跨任务总体提升。发布结论须分开陈述实现测试、真实 provider 运行和产品体验判断。
